# Artifact standards

Read [design guidance](references/design-guidance.md) and [clear-writing](../clear-writing/SKILL.md)
before you write a page. Resolve both paths from the installed skill directory, never
from the working directory. If the host also provides its own artifact design or
diagramming skills, load them as supplemental craft, subordinate to the rules below.
Their absence never blocks the work.

## The reader

Write every page for a teammate with zero context: no session history, no ticket
thread, no idea what was discussed. That reader lands cold and gets it. This holds
even when the user asks for something only they will read.

## Page shape

Copy [the page shell](assets/page-shell.html) and fill it in. It ships the palette,
the theme contract, the answer box, and the sources list already wired.

1. **Title and one-line subtitle.** Noun phrase, no colon-appended explainer.
2. **Byline.** One muted line under the subtitle: `As of <date> · <author> (<email>) with <host agent>`.
   Take the author from the current user (git `user.name` and `user.email`, or what
   they told you) and the host agent from the agent actually writing the page. Never
   hardcode either in this skill. Ask only if the identity is still missing.
3. **Answer box.** One to three lines of bottom line, in a bordered box, above everything else.
4. **Terms** (explainers only, see below).
5. **The visual.** Diagram, chart, or table. This is the payload.
6. **Sections.** As many as the topic needs. Full reference beats a teaser; length comes from scope, never padding.
7. **Sources.** A short list of links at the end (see Provenance).

No section navigation by default: the page scrolls, and clear headings carry it. Add
the sticky sidebar only when the user asks for it; the shell keeps it in a comment.

Detail that only some readers need goes in a `<details>` block, closed by default,
never persisted.

## Terms first (explainers)

When the request is exploratory or educational (explain, teach me, how does X work,
what is, walk me through), the first section after the answer box defines the concepts
the rest of the page depends on, before the page uses them. Order them from the one
the reader most likely knows to the one they least know. One or two plain sentences each.

Everywhere else, define a term on first use, inline, if a zero-context teammate might
not know it.

## Words

- `clear-writing` applies to every string on the page: headings, labels, tooltips, table cells, alt text, footers.
- Zero em dashes, including `&mdash;` and `&#8212;`.
- Zero meta-commentary: no process notes, no model names, no round counts, no session
  names, no "generated by", no how-this-was-made. The byline's host agent is the one
  allowed tool mention.
- Self-descriptive names only. Never session shorthand such as "option H", "approach 2", "the wedge", "the spine". Name the thing.
- Never coin a term or metaphor. If the plain phrase is longer, use the plain phrase.
- No emoji on the page. A publisher's own icon metadata is the one exception, where the host supports it.

## Theme (hard rule)

Light is the default, always. A viewer with no stored choice sees the light theme,
whatever their OS or host setting says. Dark is one click away on the in-page toggle
and persists for that page. Single theme only when the user asks for it in the request.

Every colour comes from a token. Two blocks:

1. `:root` holds the full light palette and `color-scheme: light`.
2. `:root[data-theme="dark"]` redefines the tokens and sets `color-scheme: dark`.

The pre-paint inline script stamps `data-theme` before first paint: `dark` if stored,
`light` otherwise. The toggle is always present and reachable. No hard-coded hex
outside the token blocks, including SVG strokes and chart colours.

The shell stores the choice under one key for the whole origin. Pages served from the
same origin can therefore share a stored preference, and browsers treat storage under
`file:` URLs differently. Both are known and accepted; do not redesign the shell.

## Palette

The palette in the page shell is the house palette. Reuse it as-is so the pages read
as one set. Add a topic accent only when no existing token can carry the meaning.

## Interactivity

Light by default: collapsible detail, tabs between views, hover tooltips, the theme
toggle. No state beyond the theme choice. Go heavier (filters, click-to-trace, search)
only when the content has several useful views and the user asks for exploration.

## Provenance

Two things, nothing more:

- The byline: date always, so a reader knows how fresh the facts are, plus author, email, and host agent.
- Links to the sources the content rests on, in a Sources section at the end. Tickets
  always. PRs, docs, dashboards, and repo files when a reader would open them. Link
  inline instead where one claim depends on one source. A local file with no URL is
  named in code font, not linked.

No confidence flags, no verified badges, no build notes.

## Content grounding

Describe behaviour from the thing that defines it: code, `SKILL.md`, manifest, config,
telemetry. Never from a roadmap, plan, or ticket description. If a claim is not
grounded, leave it out.

Ship one self-contained HTML file. Lean beats elaborate; no feature the request did
not ask for. A pinned CDN chart library is the one stated exception: the page is still
one file, but a CDN-backed chart needs the network to render.

## Charts and diagrams

Standard chart types: a pinned library from a CDN the host allows, exact version,
loaded before the inline script that uses it. Colours come from the tokens; listen for
the shell's `themechange` event and restyle. Hand-write inline SVG for anything the
library does not do well, and for any page that must render offline.

Diagrams: real mechanism, named actors, labelled edges. Colour encodes category, not
sequence, and two or three colours carry it. Inline SVG. Mermaid only where the
surface renders it. [Design guidance](references/design-guidance.md) covers the craft.

## Delivery

Always write the file first, then decide how it reaches the reader.

1. **Write one self-contained HTML file outside every repository worktree.** Use the
   host session scratchpad when one is writable; otherwise create a private directory
   under the OS temporary directory and write `<descriptive-slug>.html` there. Reuse
   the same path for revisions. If no permitted location outside the worktree is
   writable, report the missing capability instead of writing into the repository.
   Never commit a generated page.
2. **Publish only when the host has a publisher and the user's request or standing
   authorization permits it.** A tool existing is not authorization to publish.
   Follow the publisher's own documented contract. On Claude Code that is the
   `Artifact` tool: pass `title` and `description` every time, set `favicon` on the
   first publish only, keep both stable for the life of the page, redeploy by calling
   the tool again with the same file path, and update a page from an earlier session
   with `action: "list"`, then read it, then publish to that `url`.
3. **Without a publisher, hand back the file** through the host's attachment or
   clickable-file mechanism and say plainly that it is a local file, not a hosted page.
   Do not start a preview server or install a publisher by default.

Never present a local path or a `localhost` URL as a shareable web link.

## Chat reply

Two parts, nothing else.

Published to a hosted URL:

1. The bottom line in one or two lines, then the link.
2. A paste-ready Slack line in a code block: `<Title>: <one-line subtitle> <url>`.

Local file only:

1. The bottom line in one or two lines, then the file link.
2. A paste-ready Slack line in a code block: `<Title>: <one-line subtitle> (HTML file attached)`,
   plus one line telling the user to attach the file to that message.

Some hosts serve the same generic preview card for every page link. Claude Code's
`Artifact` host is one: claude.ai shows "Claude Artifact" for every artifact URL, so
the Slack message text is the only place the title and subtitle can appear. Either
way: no em dashes, no emoji, one sentence.

## Pre-publish checklist

1. No literal em dash character, and no `&mdash;` or `&#8212;` entity, anywhere in the file.
2. No slop vocabulary, throat-clearing, closing pleasantry, or summary paragraph.
3. First load with no stored choice renders light. Toggle switches to dark and back; both modes legible, diagram strokes and chart colours included.
4. Every term a zero-context teammate might not know is defined before use; explainers open with a Terms section.
5. No coined words or metaphors; no session shorthand.
6. No meta-commentary anywhere, footer included.
7. Byline present with date, author, email, and the host agent that wrote the page; Sources section lists the tickets, PRs, and docs the page rests on.
8. No sidebar unless the user asked for section navigation.
9. Wide content scrolls inside its own container; the body never scrolls sideways.
10. Title and description set. When publishing, the publisher's own metadata is filled and the icon is set on the first publish only.
11. The file sits outside every repository worktree, and the chat reply carries the matching share line: hosted URL, or local file plus the attach instruction.
